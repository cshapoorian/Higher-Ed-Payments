Higher Education Tuition Payments — Architecture & Decisions
Hyperswitch sandbox prototype · US market · Courses → Review → Payment
1. The Industry, and Why
When I think of a payment experience that needs improvement, I naturally land on higher education. There's normally so many different pieces at play: student aid, scholarships, admin fees, lab fees, and many others alike. I remember my own experience in college handling my payments and how difficult it was to manage and understand exactly what was going on. When I think of the essential user flow though, it doesn't need to be much different than what we see in modern payment UXs. When you break it down, it's as simple as selecting your classes, reviewing the details of the classes you picked and what they look like cost wise, then setting up the payment to actually confirm the purchase. In reality, there's a lot more at play that I am not including in the scope of this project which I discuss below.
2. The Flows This Industry Needs
Itemized invoicing — tuition, fees, and aid credits rolled up into a computed balance due.
Multiple funding sources on one invoice — self-pay (card/ACH), financial aid, third-party or authorized payer.
Fee-differentiated payment methods — ACH free, card surcharged.
Term-length installment / payment plans — split a balance across several scheduled charges.
Saved payment method — reused every term without re-entry.
Refunds — tied to the add/drop and withdrawal calendar, not a flat policy.
Failed-payment dunning and registration holds. 
Itemized receipts / statements for recordkeeping and 1098-T tax reporting.
Delegated, FERPA-safe access for authorized (non-student) payers.
3. What I Built vs. Deferred, and Why
Built and working end-to-end against the live Hyperswitch sandbox
Three-step journey — Courses → Review → Payment — matching the reference wireframe, with free backward navigation; once a payment is submitted, the method cards and the confirm button lock.
Course selection is intentionally a flat add/remove list — no time-conflict or prerequisite checking. That's a student-information-system problem, not a payments one, and was out of scope by design.
Review is the invoice source of truth — tuition + lab fee + admin fee, minus a financial-aid credit, producing a server-computed balance due that the client never overrides.
Card payments run real Hyperswitch sandbox transactions through the SDK's hosted fields, with the card surcharge passed to Hyperswitch as surcharge_details rather than silently folded into the amount. Verified live on 2026-09-09: a Payment Intent created by this project's own API confirms to succeeded against the sandbox's fauxpay connector, and the decline test card returns failed / DC_08.
Order status is confirmed server-to-server, never by redirect. The order only flips to Paid when Hyperswitch confirms it to the API — through its signed webhook, or through a force_sync status check the API makes itself when the webhook hasn't landed yet. The client's own confirmPayment result is deliberately discarded, so a closed tab or a dropped connection can't fake a completed payment.
An itemized PDF receipt is generated once the order is marked Paid, rendered on demand rather than written to disk so it survives an ephemeral filesystem.
Built, but not yet transacting — the gap named rather than papered over
ACH bank transfer. The whole path exists: a no-fee quote computed server-side, a bank-selection and account-details panel, and routing/account numbers collected inside Hyperswitch's hosted element rather than our own inputs. It cannot complete a payment on this merchant account, though — no bank-debit-capable connector is enabled on the business profile, and confirming returns IR_39 ("No eligible connector was found for the current payment method configuration"). That's a dashboard configuration fix rather than a code change, but until it's made, ACH is a built path with nothing behind it. The "no fee" framing is real server-side pricing logic, not a label; it just has no connector to route to.
The four-payment installment plan. The pricing, the 30-day schedule, its persistence against the order, and the secret-protected endpoint that charges due installments as merchant-initiated transactions are all built, and a later charge's webhook reconciles against its own payment record without disturbing the order's overall status. Two things stand between that and the flow described in §4: the first charge is currently created for the full balance rather than for the first installment's amount, and the customer-initiated charge doesn't yet send the mandate_data / customer_acceptance that Hyperswitch needs in order to return a mandate — so the three follow-on charges have nothing to charge against. The CIT/MIT model is the right one and the plumbing sits behind it; the mandate request itself is what's missing.
Deferred — real flows for this industry, called out rather than faked
Authorized / third-party payer. A scoped, login-less "pay this invoice" link for a parent, with FERPA-consented access limited to one invoice rather than a full student account. There is no auth of any kind in the prototype — the API hands back a single seeded student.
Refunds and withdrawal proration. Hyperswitch's Refunds API is the easy part; the real work is a policy engine (100/50/0% by drop date) tied to the academic calendar, which should exist before the refund call is wired up.
Installment dunning and registration holds. Hyperswitch's webhooks and smart retries are the right primitives, but a scheduler/dunning service and a hold flag on the student record are new surface area, deferred for time. A failed installment charge today is logged and reported in the run's results, never retried and never surfaced to the student.
Multi-payer split invoices (e.g., parent covers half). Needs partial-payment tracking per invoice, not just per Payment Intent; an invoice currently maps to exactly one order.
Saved-card reuse. The Hyperswitch Customer per student is real and idempotent, and the API lists that customer's saved cards, so "Card ending 4242 (saved)" only ever appears when a real saved method exists rather than as a hardcoded row. What's deferred is both halves of actually using it: card payments don't yet set setup_future_usage, so nothing is tokenized through the ordinary flow, and selecting the saved card still re-mounts hosted fields instead of confirming against the stored payment_method_id.
3DS and other customer-action states. Status mapping currently treats anything that isn't succeeded or processing as failed, which means a card that asks for a 3DS challenge would be reported to the student as a decline. Handling requires_customer_action properly is a small change, but an untested one without a 3DS test card in hand.
Moving surcharging into Hyperswitch. The card surcharge is already passed through as surcharge_details, so it's a real field on the payment rather than presentational. What's deferred is moving the rule itself into Hyperswitch's Surcharge Decision Manager instead of computing it in our own fee-quote service — worth doing once rates become connector-specific, unnecessary while the rule is one flat percentage.
4. Hyperswitch Integration & Payment-Method Choices
Server-authoritative Payment Intents. The storefront backend prices the cart and creates the Payment Intent server-side at the Review → Pay transition, from its own line items — the client never supplies an amount. The request the client can make carries only an invoice ID and a chosen method; the amount is re-derived from the stored invoice on every call. For a "real completed payment," this is non-negotiable: a client-supplied amount is the most common fraud vector in tuition payment portals.
Hosted card fields, not raw HTML inputs, via Hyperswitch's client SDK — keeps PCI scope at SAQ-A, appropriate for a school payment portal handling a captive audience's card data every term. The secret key stays in the API, which deliberately does not wrap the confirm call at all. Billing address and account-holder name are collected as ordinary inputs and passed as billing_details, since neither is cardholder data. One caveat: the card confirm path is verified against the sandbox over REST, but the browser widget's own mount and change behavior hasn't been exercised in a real click-through, and the confirm button is gated on that event.
Card and ACH as payment methods on one integration, not two vendor integrations. This is Hyperswitch's core value proposition earning its keep here: card and ACH have completely different settlement timelines (seconds vs. days) behind a single Payments API, instead of wiring a card processor and a separate ACH provider by hand. That's the architecture, and the API surface reflects it — method is a parameter, not a second integration. As noted in §3, only the card leg can currently transact on this sandbox account, so the payoff is designed for but unproven.
Status handling built around Hyperswitch's payment-status states, not a binary paid/unpaid. ACH intents sit in a processing state before they succeed or fail; the UI shows "processing," with a separate state for "still confirming, check back" rather than spinning indefinitely, and the order finalizes only on a server-confirmed terminal status. Card confirms same-session — treating the two identically was the wrong instinct to design around. The order state machine actually exercised is Payment Pending → Processing → Paid / Failed.
Installments via saved-payment-method mandates, not a BNPL connector. Real tuition installment plans (Nelnet, TouchNet) are financed by the institution itself, not a third-party lender — routing through an Affirm/Klarna-style BNPL connector would quietly create a consumer-lending relationship (Reg Z, state licensing) the school hasn't taken on. The design instead is: the first installment is a customer-initiated transaction that also saves the payment method (mandate); the remaining three are merchant-initiated transactions charged against that mandate on a schedule. This is exactly what Hyperswitch's CIT/MIT mandate model exists for, and it's the right mental model for merchant-financed installment plans generally, not just here. No BNPL connector is used anywhere in the project. As §3 notes, the CIT doesn't yet request the mandate, so the MIT half isn't reachable in the prototype.
Tokenized Hyperswitch Customers, one per student, reused every subsequent term. The customer is provisioned idempotently and persisted on the student record, and it's what a saved payment method hangs off — the "Card ending 4242 (saved)" option reads from a real customer lookup rather than a hardcoded row, though as §3 notes, nothing is tokenized into it yet.
Test connectors, and what production would need instead. The sandbox profile this runs against has several card test connectors and no ACH-capable one, which is the direct cause of the ACH gap above. Production is where Hyperswitch's smart routing and failover across multiple live connectors earn their keep — tuition volume concentrates into a few due-date days a term, a narrower, higher-stakes version of Black Friday, where processor failover matters more than on a smoothly distributed storefront.
5. How the Prototype Fits Together, End-to-End
1. Student adds/removes course sections client-side — no server call needed yet.
2. On Review, the client asks the storefront API to price the cart; the API returns the itemized invoice and balance due — the numbers rendered are the numbers later charged.
3. On Payment, the client asks the storefront API for a Payment Intent scoped to that balance plus the chosen method's fee; the API creates it server-side with its secret key and returns a client secret.
4. The client renders Hyperswitch's hosted fields (card) or the ACH / saved-card / installment options, and confirms the intent directly with Hyperswitch using the client secret — card data never touches the storefront API.
5. Hyperswitch routes to the sandbox connector, and card returns a result in-session. ACH would return "processing" here and settle later, which is what the processing and check-back states in the UI are built for — it's the step that can't currently run, per §3.
6. Hyperswitch sends the storefront API a signed webhook on the terminal status; the API verifies the HMAC over the raw body, updates order state, and, if paid, generates the itemized PDF receipt. If that webhook is delayed or dropped, the API's own force_sync status check reconciles through the same path — still server-to-server, never the client's word.
7. For the installment plan, the intended flow repeats steps 3–6 at 30-day intervals as MIT charges against the stored mandate, each posting its own webhook-driven ledger entry against the same invoice. The scheduling, persistence, and charge endpoint exist; the mandate they would charge against does not yet, per §3.
