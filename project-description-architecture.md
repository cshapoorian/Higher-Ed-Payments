Higher Education Tuition Payments — Architecture & Decisions
Hyperswitch sandbox prototype · US market · Courses → Review → Payment

1. The Industry, and Why
When I think of a payment experience that needs improvement, I naturally land on higher education. There's normally so many different pieces at play: student aid, scholarships, admin fees, lab fees, and many others alike. I remember my own experience in college handling my payments and how difficult it was to manage and understand exactly what was going on. When I think of the essential user flow though, it doesn't need to be much different than what we see in modern payment UXs. When you break it down, it's as simple as selecting your classes, reviewing the details of the classes you picked and what they look like cost wise, then setting up the payment to actually confirm the purchase. In reality, there's a lot more at play that I am not including in the scope of this project which I discuss below.

2. The Flows This Industry Needs
Itemized invoicing — tuition, fees, and aid credits rolled up into a computed balance due.
Multiple funding sources on one invoice — self-pay (card/ACH), financial aid, third-party or authorized payer.
Fee-differentiated payment methods — ACH free, card surcharged.
Term-length installment / payment plans — split a balance across several scheduled charges.
Saved payment method — reused every term without re-entry.
Refunds — tied to the add/drop and withdrawal calendar, not a flat policy.
Failed-payment dunning and registration holds.
Itemized receipts / statements for recordkeeping and 1098-T tax reporting.
Delegated, FERPA-safe access for authorized (non-student) payers.

3. What I Built vs. Deferred, and Why

Working end-to-end against the live Hyperswitch sandbox
Three-step journey — Courses → Review → Payment — matching the reference wireframe, with free backward navigation until a payment is submitted. Once an invoice is paid, the step collapses to a receipt rather than leaving a filled-in card form under a one-line banner, and the API refuses (409) to open a second Payment Intent against a settled invoice — without that, a student who navigated back after paying could be charged twice and the paid record would be overwritten.
Course selection is intentionally a flat add/remove list — no time-conflict or prerequisite checking. That's a student-information-system problem, not a payments one, and was out of scope by design.
Review is the invoice source of truth — tuition + lab fee + admin fee, minus a financial-aid credit, producing a server-computed balance due that the client never overrides.
Card payments run real Hyperswitch sandbox transactions through the SDK's hosted card element, with the card surcharge passed to Hyperswitch as surcharge_details rather than silently folded into the amount. Verified live on 2026-09-09, in the browser and over REST: a Payment Intent created by this project's own API confirms to succeeded against the sandbox's fauxpay connector, and the decline test card returns failed / DC_08. Hyperswitch's own error text is surfaced to the student rather than a blanket "payment failed".
Order status is confirmed server-to-server, never by redirect. The order only flips to Paid when Hyperswitch confirms it to the API — through its signed webhook, or through a force_sync status check the API makes itself when the webhook hasn't landed yet. The client's own confirmPayment result is deliberately discarded, so a closed tab or a dropped connection can't fake a completed payment.
An itemized PDF receipt is generated once the order is marked Paid, rendered on demand rather than written to disk so it survives an ephemeral filesystem.

Built, but not transacting yet — surfaced in the UI rather than papered over
ACH bank transfer. The path is built end to end: a no-fee quote computed server-side, bank selection, labelled routing/account-number fields with real ABA check-digit validation, a confirm that posts bank_debit/ach straight to Hyperswitch with the publishable key, and a "Transfer submitted" terminal state reflecting that ACH settles over days rather than in-session. Two of its three paths are verified live — an invalid routing number is rejected in the browser before any network call, and an unchargeable account is explained rather than silently failing. The success path cannot run here, and the reason is worth stating precisely, because it is not the one it first appears to be: enabling bank_debit on this profile's connectors succeeds (HTTP 200) and makes ACH show up as eligible, but every confirm then fails with IR_19 — all four connectors on the profile are Hyperswitch dummy connectors that implement cards only. Per GET /feature_matrix, only real integrations (Adyen, Stripe, GoCardless, Dwolla, Stax, Payload, Wells Fargo) support ACH, each needing that processor's own sandbox credentials. So this is a third-party account gap, not a dashboard toggle anyone forgot. Rather than hardcode that conclusion, the storefront reads GET /api/payment-capabilities, which cross-references the merchant's connectors against the feature matrix; ACH turns itself on with no code change the moment a capable connector is added. The "no fee" framing is real server-side pricing logic, not a label; it simply has no connector to route to.
The four-payment installment plan. The pricing, the 30-day schedule, its persistence against the order, and the secret-protected endpoint that charges due installments as merchant-initiated transactions are all built, and a later charge's webhook reconciles against its own payment record without disturbing the order's overall status. The two gaps described in the previous version of this section — the intent being created for the full balance instead of the first installment, and the first charge not requesting a mandate at all — are now fixed: the intent is created for `installmentSchedule[0].amountCents`, and it sends `mandate_data.customer_acceptance` plus a `mandate_type.multi_use` cap equal to the fixed amount of installments 2–4, so a successful first charge should come back with a `mandate_id` for `services/orderStatus.ts` to store (that storage path already existed and needed nothing new). Two things are still open, and this hasn't been run against the live sandbox yet: `customer_acceptance`'s fields and the `single_use` variant of `mandate_type` are confirmed against Hyperswitch's own OpenAPI reference, but the `multi_use` variant sent here is inferred from that same amount/currency shape, not independently confirmed — a real payment needs to be run through to see whether Hyperswitch actually hands back a `mandate_id` on this exact request. And even with a mandate, nothing in this environment calls `POST /api/installments/run-due` on a schedule — no cron/scheduler is deployed (see `render.yaml`) — so payments 2–4 would be chargeable but still wouldn't be collected without a person or a job hitting that endpoint. The payment page's disclosure now says exactly that, rather than either overclaiming automatic billing or its previous "charges the whole balance" state.

Webhook signature verification remains unverified against a real Hyperswitch delivery, unchanged from before — see ENDPOINTS.md. It was deliberately left alone this round in favor of the installment mandate fix above, which was judged the higher-value gap to close: it's pure code with no external dependency, and it's the centerpiece of this project's CIT/MIT design, whereas confirming the webhook needs a deployed URL registered in Hyperswitch's dashboard, which depends on hosting being set up first. The order-state transition the webhook drives (`applyHyperswitchStatus`) is exercised constantly, since the force_sync path on every order-status poll calls it too — what's specifically unverified is the raw-body HMAC check standing in front of it, `verifyWebhookSignature`, which the force_sync path doesn't go through at all (it's a direct, secret-key-authenticated GET, not a signed push).

Deferred — real flows for this industry, called out rather than faked
Authorized / third-party payer. A scoped, login-less "pay this invoice" link for a parent, with FERPA-consented access limited to one invoice rather than a full student account. There is no auth of any kind in the prototype — the API hands back a single seeded student.
Refunds and withdrawal proration. Hyperswitch's Refunds API is the easy part; the real work is a policy engine (100/50/0% by drop date) tied to the academic calendar, which should exist before the refund call is wired up.
Installment dunning and registration holds. Hyperswitch's webhooks and smart retries are the right primitives, but a scheduler/dunning service and a hold flag on the student record are new surface area, deferred for time. A failed installment charge today is logged and reported in the run's results, never retried and never surfaced to the student.
Multi-payer split invoices (e.g., parent covers half). Needs partial-payment tracking per invoice, not just per Payment Intent; an invoice currently maps to exactly one order.
Saved-card reuse. The Hyperswitch Customer per student is real and idempotent, and the API lists that customer's saved cards, so "Card ending 4242 (saved)" only ever appears when a real saved method exists rather than as a hardcoded row. Both halves of using it are deferred: card payments don't set setup_future_usage, so nothing is tokenized through the ordinary flow, and selecting the saved card still confirms through the same hosted card element rather than a one-click charge against the stored payment_method_id.
3DS and other customer-action states. Status mapping treats anything that isn't succeeded or processing as failed, so a card that asks for a 3DS challenge would be reported to the student as a decline. Handling requires_customer_action properly is a small change, but an untested one without a 3DS test card in hand. Relatedly, the Draft and Reviewed order states exist in the type union but are never assigned — the machine actually exercised is Payment Pending → Processing → Paid / Failed.
Moving surcharging into Hyperswitch. The card surcharge is already passed through as surcharge_details, so it's a real field on the payment rather than presentational. What's deferred is moving the rule itself into Hyperswitch's Surcharge Decision Manager instead of computing it in our own fee-quote service — worth doing once rates become connector-specific, unnecessary while the rule is one flat percentage.

4. Hyperswitch Integration & Payment-Method Choices
Server-authoritative Payment Intents. The storefront backend prices the cart and creates the Payment Intent server-side at the Review → Pay transition, from its own line items — the client never supplies an amount. The request the client can make carries only an invoice ID and a chosen method; the amount is re-derived from the stored invoice on every call. For a "real completed payment," this is non-negotiable: a client-supplied amount is the most common fraud vector in tuition payment portals.
Hosted card fields, not raw HTML inputs, via Hyperswitch's client SDK — keeps PCI scope at SAQ-A, appropriate for a school payment portal handling a captive audience's card data every term. The secret key stays in the API, which deliberately does not wrap the confirm call at all. Billing address is collected as ordinary inputs and passed as billing_details, since it isn't cardholder data. Bank routing and account numbers are also ordinary labelled inputs: that's bank data, outside PCI's cardholder-data scope, and it still goes from the browser to Hyperswitch rather than through our API. Mounting Hyperswitch's unified "payment" element there was tried and removed — on this account, with no bank-debit connector enabled, it falls back to rendering a card form, which under a "Link your bank" heading would invite a student to type card data into what they believe is a bank transfer. ACH therefore confirms through a direct POST /payments/{id}/confirm with the publishable key rather than through the SDK: same origin for the data (browser → Hyperswitch, never our API), same credential the SDK would use, but no element to mount.
What live SDK verification changed. The integration was first written to the Stripe.js shape, assuming an element "change" event carrying { complete } to gate the Pay button. Verified against the real HyperLoader on 2026-09-09: the global is window.Hyper and elements.create("card") does mount a working card iframe, but the element emits only ready, focus and blur — there is no change event, so per-keystroke validity is not observable. Gating Pay on it left the button disabled forever. The Pay button now gates on what is observable (the iframe having painted, our own fields being complete), and card validity is reported by confirmPayment rejecting, whose message is shown to the student. Worth recording because it's the kind of assumption that looks correct in review and only fails in a browser.
Card and ACH as payment methods on one integration, not two vendor integrations. This is Hyperswitch's core value proposition earning its keep here: card and ACH have completely different settlement timelines (seconds vs. days) behind a single Payments API, instead of wiring a card processor and a separate ACH provider by hand. That's the architecture, and the API surface reflects it — method is a parameter, not a second integration. As noted in §3, only the card leg can currently transact on this sandbox account, so the payoff is designed for but unproven.
Status handling built around Hyperswitch's payment-status states, not a binary paid/unpaid. ACH intents sit in a processing state before they succeed or fail, so the two methods have different destinations, not just different speeds: for a card, "processing" is a transient blip worth waiting through, while for ACH it *is* the resting state, and the UI stops there with "Transfer submitted" instead of polling to a misleading timeout. The order still finalizes only on a server-confirmed terminal status. Statuses that mean "in flight" — requires_customer_action in particular, which is how an ACH mandate authorization surfaces — are explicitly non-terminal rather than falling through to failed; recording them as failures would mark live payments dead. Card confirms same-session — treating the two identically was the wrong instinct to design around.
Installments via saved-payment-method mandates, not a BNPL connector. Real tuition installment plans (Nelnet, TouchNet) are financed by the institution itself, not a third-party lender — routing through an Affirm/Klarna-style BNPL connector would quietly create a consumer-lending relationship (Reg Z, state licensing) the school hasn't taken on. The design instead is: the first installment is a customer-initiated transaction that also saves the payment method (mandate); the remaining three are merchant-initiated transactions charged against that mandate on a schedule. This is exactly what Hyperswitch's CIT/MIT mandate model exists for, and it's the right mental model for merchant-financed installment plans generally, not just here. No BNPL connector is used anywhere in the project. As §3 notes, the CIT now requests the mandate; what's unproven is whether Hyperswitch actually returns a mandate_id for the specific mandate_type.multi_use shape sent, and, separately, nothing in this environment schedules the MIT charges even once a mandate exists.
Tokenized Hyperswitch Customers, one per student, reused every subsequent term. The customer is provisioned idempotently in both directions — against our own database and against Hyperswitch, which is the case that actually bites: a re-seed or a crash between the create call and the write leaves the customer live at Hyperswitch while our column reads null, and retrying then fails with IR_12. Since the customer id we send is the student id, an IR_12 means the customer we wanted already exists, so it's adopted rather than treated as an error. The customer is what a saved payment method hangs off — the "Card ending 4242 (saved)" option reads from a real customer lookup rather than a hardcoded row, though as §3 notes, nothing is tokenized into it yet.
Test connectors, and what production would need instead. The sandbox profile this runs against has several card test connectors and no ACH-capable one, which is the direct cause of the ACH gap above. Note also that the REST API and the client SDK are served from different hosts — the API from sandbox.hyperswitch.io, HyperLoader.js from beta.hyperswitch.io — which is why the web app carries its own SDK URL. Production is where Hyperswitch's smart routing and failover across multiple live connectors earn their keep — tuition volume concentrates into a few due-date days a term, a narrower, higher-stakes version of Black Friday, where processor failover matters more than on a smoothly distributed storefront.

5. How the Prototype Fits Together, End-to-End
Components: a three-step storefront SPA; a storefront API that owns invoicing and order state (Payment Pending → Processing → Paid / Failed; Draft and Reviewed are declared but unused); Hyperswitch (Payment Intents, Customers, Mandates, Webhooks); card test connectors on the sandbox profile, with no ACH-capable connector enabled; a receipt generator.
1. Student adds/removes course sections client-side — no server call needed yet.
2. On Review, the client asks the storefront API to price the cart; the API returns the itemized invoice and balance due — the numbers rendered are the numbers later charged.
3. On Payment, the client asks the storefront API for a Payment Intent scoped to that balance plus the chosen method's fee; the API creates it server-side with its secret key and returns a client secret. If the invoice is already paid, it returns 409 instead.
4. The client renders Hyperswitch's hosted card element (card, saved card, and the installment plan, all of which are card-funded) or the ACH fields, and confirms the intent directly with Hyperswitch using the client secret — card data never touches the storefront API.
5. Hyperswitch routes to the sandbox connector, and card returns a result in-session. ACH returns "processing" here and settles later, which is what the submitted and check-back states are built for — it's the step that can't currently run on this account's connectors, per §3.
6. Hyperswitch sends the storefront API a signed webhook on the terminal status; the API verifies the HMAC over the raw body, updates order state, and, if paid, generates the itemized PDF receipt. If that webhook is delayed or dropped, the API's own force_sync status check reconciles through the same path — still server-to-server, never the client's word.
7. For the installment plan, the intended flow repeats steps 3–6 at 30-day intervals as MIT charges against the stored mandate, each posting its own webhook-driven ledger entry against the same invoice. The scheduling, persistence, charge endpoint, and now the mandate request on the first charge all exist, per §3; what's still needed is a live run confirming Hyperswitch returns a mandate_id for it, and something external actually calling the charge endpoint on the 30-day cadence.
Data model: Student · Term · Invoice (line items incl. aid credit, computed balance_due) · Order · Payment (Hyperswitch payment_id, method, status, amount) · InstallmentPlan (mandate_id + schedule) · Receipt.
